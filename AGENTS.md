# AGENTS.md

Your operating manual for this workspace, written by you. Your main instructions cover how you work in general. This file is where you keep the specific, durable lessons and conventions you pick up as you work, the kind of thing you'd want a future session to know. It's not about the user (that goes in `USER.md` and your memory) or your personality (that's `SOUL.md`); it's about how you get work done here.

## Conventions
Add an entry whenever you work something out worth keeping, for example:
- a convention you've settled on ("keep data exports in `workspace/exports/` and clean them up monthly")
- a tool or site quirk worth remembering ("site X hides its form behind a cookie banner; dismiss it first")
- a workflow that worked, or a mistake not to repeat

It starts empty and is meant to grow slowly. Don't pad it; a short, accurate file beats a long, stale one.

## subhub-specific notes
- `pnpm test` / `pnpm typecheck` (`tsc --noEmit`) / `pnpm build` are the gate. Root `tsconfig.json` covers `tests/` but not `pages/`; the build is what type-checks the Vue SFCs.
- No DOM test environment (no jsdom/happy-dom) is installed: keep page logic in pure helpers under `core/utils/` and unit-test those instead of mounting components.
- Admin page error banners must go through `core/utils/api-error.ts` (`apiErrorMessage`). The old per-page `err.data?.error ?? fallback` pattern returns `''` for non-API exceptions, which renders a *blank* red banner (the item-3 silent-failure symptom).
- Running the built server for smoke tests: pick a free port; 3999 may already be occupied by an unrelated long-running process on this machine. Use a throwaway `SUBHUB_DB_PATH` and kill only the PID you started.
- The UI design system is light-only now: `--primary`/`--accent` = trust blue #2563EB (CTA, links, active nav, ring), green #16A34A (`--success`) is reserved for success badges/notices. Adding a green CTA or a dark `color-scheme` back would regress the owner's rejected dark theme.
- Source access model v2 lives in `server/utils/admin-sources.ts` (parsing/consistency) + `loadUserSourceCaches` in `server/utils/export-nodes.ts` (who sees what). SQLite sorts NULL *before* integers, so `ORDER BY owner_user_id` puts public rows first — the dedicated-first ordering is done in JS, don't "simplify" it back into SQL.
- Page chrome: pages render `<PageTopbar title subtitle>` themselves (in `components/`). A page-level `<template #topbar>` does NOT reach `layouts/admin.vue`; layout slots only flow from `<NuxtLayout>`.
- `core/utils/admin-ui.ts` holds the pure page logic (source grouping/health, 归属 summaries, form payloads, log chips, time labels). Keep it import-relative (`../../server/utils/...`), not `~/…`: the root `tsc --noEmit` has no Nuxt alias table (only `nuxt build` does).
- Dashboard quick actions deep-link `?new=1` on /users, /sources, /profiles to open the create form; /preview accepts `?userId=`.
- DNS/QUIC anti-leak template: `core/dns.ts` owns `BUILTIN_DNS_TEMPLATE` (fake-ip, DoH only, `listen` deliberately omitted; `respect-rules: true` REQUIRES a non-empty `proxy-server-nameserver` — mihomo rejects the whole config without it) + `parseDnsTemplate`; `core/producers/mihomo.ts` owns `QUIC_BLOCK_RULE`/`buildLeadingRules`/`stringifyMihomoConfig`. `produceMihomo()` now emits `dns:` + `proxies:` + `rules:` for mihomo/clash only; every other target has its own producer (see the `renderTargetBody` note below) — do not route them through `produceMihomo`. The plan is to move DNS+QUIC into query params later; until then they are on by default (owner-approved 2026-10).
- Export target `clash` renders **exactly** like `mihomo` (`renderTargetBody` handles both with the same producer): modern Clash clients are mihomo-based. The old legacy-Clash producer (whitelist that dropped vless/anytls/tuic/hysteria2 → `proxies: []` for modern users) is deleted — do not reintroduce a per-target node filter. The profile `variant` (`mihomo`/`legacy`) still only affects how *rules* are expanded.
- `subscription-userinfo`: parsing/aggregation lives in `server/utils/userinfo.ts` (pure, shared by the refresh task, the export and the admin DTO); parsed parts are stored per source in `userinfo_*` columns. A successful refresh without a parseable header **keeps** the previous numbers (documented in the task), and `/s/:token` emits no header at all when no visible source has any. Never re-add a placeholder header.
- Dashboard SSR gotcha: `$fetch` inside a page's `onMounted` runs only on the client, so the server-rendered HTML (and the first paint) shows the empty default state — that is how 源健康 showed "所有订阅源状态正常。" with 16 failing sources. Use `useAsyncData` + `useRequestFetch()` (the bare `$fetch` is anonymous during SSR and gets the admin-set 401) for data the first paint must show, and let a pure helper (`sourceHealthCard` in `core/utils/admin-ui.ts`) decide loading / error / empty / healthy / unhealthy. When smoke-testing the dashboard, curl the HTML **with** the session cookie and grep the rendered state; it should already be correct without JS.
- `yaml`'s `parse()` resolves *keys* through the YAML 1.2 core schema (`on`/`yes`/`NO` etc. can become non-strings, then look like duplicates). User-supplied YAML mappings (dnsTemplate) are parsed from the node tree in `core/dns.ts` (`parseDocument` + custom walk, plus `document.toJS({maxAliasCount})` for the alias guard) — keep it that way for any new user-YAML field.
- `yaml`'s `parseDocument` takes no `maxAliasCount` (that option lives on its *second* `toJS()` call); `parse()` takes it directly.
- Node's global `fetch` hangs in this sandbox (proxy-aware egress that the `https` module does not use), so any test reaching the real task's `fetch` times out instead of failing. Stub `globalThis.fetch` with `vi.spyOn` in those tests — that also documents the offline contract.
- Line-based client producers (`surge`, `loon`) share `core/producers/groups.ts` (`buildLineGroups`): members are pruned to *emitted* node names + the client's built-ins + still-alive groups, iterated to a fixpoint, and an emptied group is omitted. Don't "simplify" that back into a single pass — dropping a group must also drop references to it from other groups, or the config references an undefined group. (The fixpoint must intersect the alive set with the *useful* set — groups that can reach a real outbound — or a pure group cycle loops forever; this hung the test suite once.)
- Every export target has a real producer now: `renderTargetBody` dispatches mihomo/clash → YAML, shadowrocket → base64 share links, surge/loon → line formats, singbox → JSON outbounds, uri → base64 share links. `isFallbackTarget` / `renderMihomoFallbackBody` remain only as the opt-in path for a future target. Content types / file extensions come from `contentTypeForTarget()` / `fileNameExtensionFor()` in `server/utils/targets.ts` (singbox json, uri/shadowrocket `.txt`, surge/loon `.conf`, else yaml); `exportProfileCapability()` in `export-nodes.ts` decides whether a profile contributes groups (surge/loon), rules (mihomo/clash) or nothing (shadowrocket). Profile group regexes are expanded against `targetProxyNames()`, never raw node names.
- Shadowrocket output is `base64(links.join('\n'))` with no trailing newline; an empty export is `''` (valid empty document), never a fake node. SSR params are plain padded base64, *not* percent-encoded — the repo's `parseSsr` rejects `%3D`. SS SIP002 user info is unpadded base64url.
- Surge supports anytls (iOS 5.17.0+ / Mac 6.4.3+, AnyTLS v2): `name = anytls, server, port, password=, sni=, skip-cert-verify=` (UDP over TCP, no extra param) — do not re-add the old "Surge has no AnyTLS" skip. Surge still has **no** VLESS and no SSR, and no hy2 `up` param (only `download-bandwidth`); hy2 port hopping is `port-hopping=60000;61000-62000` (SEMICOLON-separated entries, `surgePortHopping()` converts the repo's comma form) + `port-hopping-interval=`. Loon has VLESS/anytls/ssr but no Reality, h2 transport or ss plugins, and no `load-balance` group (its fallback keyword is `fall-back`).
- Share-link producers must not skip a node just because a field needs a bit more writing: every field with a link-level expression gets emitted (hy2 `ports` → `mport=`, `up`/`down` → `upmbps=`/`downmbps=`, `hop-interval` → `hop-interval=`). The old shadowrocket hy2 builder returned `null` for those and silently dropped 11 of 71 real nodes. Shadowrocket still keeps its own builder (padded-base64 SSR params, `insecure=0` for an explicit `false`) instead of reusing `uri.ts` wholesale.
- `[common] exclude_remarks` (subconverter info/ads pseudo-node filtering) lives in `core/rules/exclude-remarks.ts` (`compileExcludeRemarks` / `excludeRemarkNodes`, exported from `../core`): `new RegExp(pattern)` with no flags (case-sensitive substring test on the node *name*), invalid/empty/missing pattern → no-op, empty name → kept. It is applied inside `loadUserProfile` (`server/utils/export-nodes.ts`), which now takes the node list and returns `{ profile, nodes }` — one INI load per export, filter **before** `targetProxyNames`/group expansion, so `.*` groups can never list a dropped node. Both callers (`subscription.ts`, `admin-preview.ts`) must render `loaded?.nodes ?? nodes`, never the raw list. It applies to every target (it is a node filter, not a Clash feature), including shadowrocket; `subscription-userinfo` aggregation is source-level and deliberately unaffected.
- Per-request rule-profile override (`feat/profile-suffix`): a subscription URL may select its profile by NAME instead of the user's `users.profileId`. Forms: `/s/<token>` and `/s/<token>/<target>` are unchanged; `/s/<token>/<target>/<profileName>` adds the override; `/s/<token>/<profileName>` is the override with the default (User-Agent) target. **Resolution order: a target wins in position 2** — when a profile is also named like a target, `/s/<token>/clash` is still the clash target, and that profile is only reachable as `/s/<token>/clash/clash`. Names match exactly (case-sensitive) against `profiles.name`, resolved once (`resolveProfileIdByName` in `export-nodes.ts`); an **unknown name is a 404**, never a silent fallback to the assigned profile. A 2nd segment that is neither target nor profile is now a 404 too (base main answered 400 there — the spec chose 404; `tests/subscription-route.test.ts` still covers the *unknown target* 400, which is the 3rd-segment/absent-profile path). Nitro routing: three route files (`index.get.ts`, `[target].get.ts`, `[target]/[profile].get.ts`) all point at `export-handler.ts`, and `requestFromEvent` decides the segment shape **from the raw path only** — `event.context.params` differs per route file and must not be used to decide which segment is which (it would misread position 2 as an override). The override drives everything the profile drives (groups/rules/rule-providers/dnsTemplate/`exclude_remarks`) by passing the resolved id as `loadUserProfile`'s 6th arg; `users.profileId` is never modified. Admin preview parity: `POST /api/admin/preview {userId, target?, profile?}` (unknown name → 404, same `resolveProfileIdByName`); the response echoes `profile`. Access logs record the target only — adding the profile name would need a schema column, so it is deliberately skipped.
- Secret admin entrance + page gate: `core/utils/admin-entrance.ts` owns the pure logic (`parseAdminPath` / `gateScope` / `decideGate`), `server/utils/admin-gate.ts` the signed cookie, `server/middleware/00-admin-gate.ts` the wiring. **The gate is always on** (default entrance `/admin`), so a fresh browser at `/` sees a blank 200 page until it visits the entrance once — this is the intended product behaviour, not a bug; do not add a dev switch or a "skip when NODE_ENV !== production" shortcut. Admin pages and `/api/admin/*` without the gate cookie get an empty 200 `text/html` body and **never** a redirect (a redirect reveals the entrance). Never gated: `/s/*` (subscriptions must keep working byte-for-byte), `/api/admin/login` + `/api/admin/logout` (a browser that just knocked lands on `/login` and still has to be able to submit the form), and non-admin `/api/*`. `SUBHUB_ADMIN_PATH` invalid/unset → `admin`; reserved first segments `s`/`api`/`_nuxt`. The cookie value is a signed token (`v1.<iat>.<exp>.<hmac>`, 30 days, `subhub_gate`), never the path — a raw `<path>` cookie must keep failing `verifyGateToken`. Nitro runs `server/middleware/*` in filename order: that is why the session gate was renamed `01-admin-auth.ts`; keep any new gate-ish middleware off `00-`-prefixed numbers unless it must run in front.
- Nitro's own public-asset layer answers `/_nuxt/<hash>.js` *before* app middleware, so hashed build assets are reachable without the gate cookie; only unknown `/_nuxt` paths reach the middleware (it answers 404). That is fine (the HTML is gated first, and there is no secret in compiled JS), but do not write a test asserting "asset 404 without cookie" against the real server.
- Tests calling admin API handlers directly bypass the Nitro middleware entirely (they never see the gate), so they must not be "fixed" by weakening it. The gate tests (`tests/admin-gate.test.ts`) drive the middleware first and then call the route, minting the cookie through `issueGateToken()` / a real knock — never by hand-writing `subhub_gate`.
- Subscription prefix (`sub_path`) is an **in-app setting**, not an env var (owner explicitly rejected env). Storage: the `settings` key/value table in `server/db/schema.ts` + `CREATE TABLE IF NOT EXISTS settings` in `server/db/index.ts` (no migration framework here — `ensureAddedColumns`/idempotent DDL is the style; the table is additive, existing DBs get it on next boot). All rules live in `server/utils/settings.ts`: `validateSubPath` (trim/slash-strip/segment-collapse, `/^[a-z0-9][a-z0-9_-]*$/` per segment, ≤4 segments, ASCII-lowercased, not the admin path `adminEntrancePath()` = `SUBHUB_ADMIN_PATH` or `admin` (matches the admin-gate default), not a reserved root `api/_nuxt/login/users/sources/profiles/preview/logs`), `getSubPath`/`setSubPath` (`ValidationError` → 400, old value untouched), and `cachedSubPath` (no wall-clock TTL on purpose: the cache is invalidated by `PUT /api/admin/settings` and by any direct `getSubPath` read; a TTL would both delay saves and force sleeps in tests).
- Serving: `server/routes/s/` stays the single implementation. `server/middleware/sub-path.ts` rewrites `/<prefix>/…` → `/s/…` and answers `/s/…` with 404 while a custom prefix is active (`decideSubscriptionRewrite` is the pure, tested decision; there is NO env override for the prefix — tests seed the server DB via `__setServerDbForTest`). **Two h3 traps cost a debugging session each:** (1) `event.path` is a *getter* (`_path || req.url`) — assigning it throws "Cannot set property path … which has only a getter" and 500s; (2) `createAppEventHandler` writes `event._path = _layerPath` before *every* stack layer from a single path snapshot taken before middleware, so a plain `event._path = …` is silently reverted and the request falls through to the Vue page router (302 to /login for `/dl/<token>`). The fix: redefine `_path` on the event as an accessor whose setter ignores further writes (`rewritePath` in sub-path.ts) — verified against the built server, not just unit tests. Middleware must run before the Nuxt render handler; Nitro registers `server/middleware/*` ahead of route handlers, which is the case here.
- Admin link building always uses the effective prefix: `subscriptionUrlWithPrefix` / `subscriptionPathLabel` in `core/utils/admin-ui.ts` (prefix from the `admin-sub-path` useState seeded by `layouts/admin.vue` from `/api/admin/me`'s `subPath`, updated immediately by the settings page). `subscriptionUrl()` is the legacy two-arg form that assumes the default `s`. `/api/admin/stats` also carries `settings: { subPath }` (that payload is where the UI gets runtime info). The settings UI is `pages/settings.vue` (nav 设置).
- User tokens: `POST /api/admin/users/:id/reset-token` (existing, now labelled 刷新令牌) regenerates via `generateUserToken()` (32 bytes hex — never weaken it); `PUT /api/admin/users/:id/token` with `{ token }` sets a custom one via `parseCustomToken` (8–64, `/^[a-z0-9][a-z0-9_-]*$/i`, case-sensitive) + `setUserToken` in `server/utils/admin-users.ts` (unique across users → 409, malformed → 400; the unique index is the race backstop). Nothing caches token→user: the export looks the user up by token per request, so logs/exports follow a rotation instantly. `ValidationError`'s status union is `400 | 404 | 409`.
- Empty-group pruning (mihomo rejects a *whole* config over one `proxy group[N]: 'use' or 'proxies' missing`): `core/rules/prune-groups.ts` (`pruneEmptyGroups`, exported from `../core/rules`), called **once** in `loadUserProfile` right after `buildRules` and before the profile leaves the function, so every target inherits it; the returned `groupNames` are the *surviving* groups only. Invariant to keep: a rendered group always has ≥1 member (a `relay` ≥2 — a 1-hop relay is not a chain), and every member/rule policy resolves to a surviving group, an emitted node, or a builtin (`BUILTIN_GROUP_MEMBERS`: DIRECT/REJECT/REJECT-DROP/PASS; `minGroupMembers()` owns the per-type minimums). Liveness is one definition: a group is live when its references are reachable from an outbound (node/builtin) — a pure cycle never reaches one, so it dies, and the scan is a bounded fixpoint so it terminates. Rules whose policy names a dropped group are removed (a dead `MATCH` group does not leave a dangling `MATCH`); order is preserved; an untouched profile is returned as the *same object* so output stays byte-identical. Call it with `nodeNames` (the target's emitted names) **and** `groupNames` (every INI-declared group: a repeated name is one group in the YAML list, defined by its last declaration). Without `nodeNames` only builtins count as outbounds — never "every unknown name is a node", that kept empty groups alive. Surge/Loon still prune inside `buildLineGroups` against their own emitted names; do not port this prune's rules into their producers (their existing tests are the contract; verified byte-identical to main for the same profile).
